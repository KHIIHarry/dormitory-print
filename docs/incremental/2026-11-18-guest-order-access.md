# 2026-11-18 游客订单与账号归属升级说明

本次同时更新前端、API、生产队列 DTO 与数据库。生产端 DSH 请按此说明与现有 [部署手册](../DEPLOYMENT.md)、[备份恢复手册](../BACKUP-RESTORE.md) 同步发布。GitHub main 更新不代表生产部署已执行。

## 拉取与发布顺序

1. 在生产仓库确认当前分支为 `main`、工作区没有未处理修改；保留生产环境文件、数据卷和原 `DORMPRINT_SECRET_KEY`。执行 `git pull --ff-only origin main`；若出现本地提交分叉或文件冲突，先核对差异，勿强制覆盖。
2. 安排维护窗口并暂停业务写入；停止旧 API、文件 worker、业务 worker 和 beat，防止旧代码在迁移期间继续创建或修改订单、授权。按现有方案创建并验证数据库与私有文件恢复点，保留对应代码版本和独立保存的主密钥。
3. 构建正式前端：`npm ci --legacy-peer-deps`、`npm run build`。生产勿使用 `npm run build:demo`。重建后端的 `api`、`file-worker`、`business-worker`、`beat`、`migrate` 镜像，保证迁移任务使用此次代码构建的镜像。
4. 执行现有迁移入口：`docker compose -f deploy/compose.yaml --env-file deploy/.env run --rm migrate`（非 Compose 环境使用 `python -m app.cli migrate`）。目标 Alembic head 为 `ce72aa117014`，直接父版本为 `b8c10d2e4f16`；较旧环境应由 Alembic 顺序执行缺失迁移。
5. 迁移成功后再同步启动新 API、两个 worker、beat，并发布正式前端产物。按已有部署方式重建/更新 proxy，确保全部服务运行同一版本。迁移失败时保持旧写入停止，先处理错误，不让新旧后端混跑。
6. 核对健康检查和 worker 日志，验证以下清单后恢复业务入口。PWA/浏览器中仍打开旧页面的用户需要刷新，载入新前端；旧 API 入口不会继续提供旧的授权能力。

## 本次迁移的实际影响

- 新增订单当前归属 `owner_account_id`、游客访问版本 `guest_access_version`、当前链接密文 `encrypted_token`，并对每单唯一未撤销游客根授权建立部分唯一索引。归属与下单时账号快照分开，后续关联不会改写原 `checkout_account_id`。
- 历史订单以可靠 principal 关联和结算账号快照回填。若二者指向不同账号，迁移会停止并输出待核对订单 ID。请人工核对后再迁移，不能按邮箱、昵称或手机号猜测归属。
- 已归属账号的订单停止全部旧游客链接与派生会话。未归属订单仅保留最新、符合条件的一个有效根链接，截止时间收紧到原到期时间与签发后 14 天中的较早时刻。其他链接、历史派生授权和相关会话失效。
- 迁移清理旧订单/授权相关幂等响应，避免旧请求键继续重放私有正文、访问凭据或旧 cookie。过期、关闭、重置和关联后的订单、附件、文件列表、已完成上传会话均按新权限校验。
- 历史链接只有哈希，后台不能恢复原始 URL。符合新期限的原链接可以继续使用；后台显示「重置后可从后台打开」时，需要管理员明确重置。重置会废止旧链接，新链接有效期可选 1–14 天，默认 14 天。
- 本次无需新增环境变量；必须保留原主密钥。它用于现有加密数据及新链接密文，替换密钥会使历史加密载荷无法读取。

## 生产验收清单

- 登录下单只通过账号所有者查看，不再签发游客链接；后台显示「客户信息」。小人图标仅标识原登录下单来源，具备 `customer.manage` 时可打开客户详情；游客后来关联账号不会改变历史下单来源。
- 游客新单仅一个有效链接，默认 14 天。有效页显示剩余天/小时、注册登录引导，并有统一品牌页眉、页脚和手机底部导航。倒计时归零时不再展示私有内容。
- 订单页返回导航放在游客提示上方；注册登录引导紧随说明文字，采用同字号、异色下划线链接。订单详情与联系管理员页的提取码后仅保留一个复制图标，直接复制包含提取码、金额、昵称的完整联系文案；不再单独显示联系文案模块。提取码标签、数值和图标水平排列、垂直居中，触控区域仍为 44 px。游客提示采用紧凑排版，标题与倒计时可同排，窄屏自然换行。
- 管理员打开、关闭、重置游客链接后检查旧链接和已打开的旧链接会话；它们不能继续读取订单或私有文件。打开/关闭/重置需要 `order.access-link.manage`，人工关联另需 `customer.manage`；两项权限都要核对。
- 原下单设备登录已验证账号后，可明确确认关联单笔订单；转发链接持有者不能自行认领。关联成功后后台自动切换「客户信息」，其他游客订单和未提交草稿保持各自权限。
- 到期/关闭页保留统一页眉、页脚和手机底部导航。「联系管理员」进入 `/u/help#contact-admin`，定位现有联系方式卡片；生产请确认联系方式已配置。
- 登录过期或被新设备挤下线后，「重新加载」引导重新登录；网络临时异常仍提供重试。
- 打印中心、装订中心、订单管理、售后等复用提取码组件。仅生成识别页的订单显示独立识别页进度；实际文件完成数单独计算。新生成识别 PDF 在二维码旁显示配送校区，旧不可变 PDF 不覆盖。预览有首页/末页双箭头。

## 回退限制与验收范围

本迁移不会在降级时重新开放已撤销链接。若上线后已发生新的独立订单归属（`orders.owner_account_id` 非空且与 `principals.account_id` 不一致），Alembic downgrade 会直接 `RuntimeError` 并要求使用部署前备份恢复，避免订单变回游客单；它不会删除这类归属列。即使不存在这种不一致，成功 downgrade 仍会先把全部 `order_access_grants` 的 `revoked_at` 置位、清空 `encrypted_token`，撤销全部 `kind='ORDER_ACCESS'` 的 `auth_sessions`，再删除 `encrypted_token`、`guest_access_version`、`owner_account_id` 等列。也就是说，降级会作废所有游客链接、链接密文和已有游客会话，不能保留为可用的游客访问。上线后已有新账号归属或需要保留游客访问时，应前向修复，不要降级；需要整库恢复时，先核对上线后新增订单、收付和履约事实，再按备份恢复手册执行，不能只回滚代码。

本地已完成 PostgreSQL 历史结构迁移、唯一约束、并发、旧请求重放和私有资源专项测试；完整页面用实际 Chrome + API + PostgreSQL 验证，有效/到期/关闭三个状态检查 320、375、390、430、768、1440 px。Chromium/WebKit 自动化为浏览器模拟，未包含 iPhone Safari、微信内置浏览器、已安装 PWA 及真实邮件客户端的物理设备验收，请生产端分别检查这些环境。
