## 2. 当前代码线索与必须修复的断点

以下为编写时的源码事实，实施前核实最新版：

1. `backend/app/commerce.py::settle_order` 在人工结算时确认时段、占用容量并进入生产，但没有自动建批/归批。
2. `backend/app/delivery.py` 的批次创建、编辑、发布、开始和 preview/commit 仍以人工调度为主；改期可能移除原 `slotId` 关联。
3. `DeliverySlot` 和时段 DTO/表单缺少完整的开放下单时间和截单时间。下单检查已有 JSON `cutoffAt` 线索，但创建、更新、公开可选判断、确认收款没有形成统一规则，不能直接认为已实现。
4. `_slot_view`、`public_slots` 与用户 `review.tsx` 对 `enabled/selectable` 的使用不一致；不能只增加前端隐藏。
5. 已有 `DELIVERY_UPDATED` 模板和 `notify_delivery_updated`，目前用于客户修改楼栋；批次改期没有形成完整通知链，模板也缺少前后时间和原因。

7. 用户订单视图和配送详情存在不同的数据来源；必须核查 `commerce.order_view`、`delivery_order_view`、store 和邮件，保证客户真的获得最新安排。
8. `src/lib/resources.ts` 部分管理场景仍读取 `/public/slots`；公开时段过滤收紧后，后台不能因此失去已截单或历史时段的展示。
9. 既有批次开始允许早于预计配送时间；本轮不得恢复“必须到预计开始时间才能出发”的旧限制。

## 3. 范围与业务名词

必须区分：

| 名词 | 含义 |
|---|---|
| 配送时段 | 用户申请的日期与预计配送窗口，以及接单时间、容量等配置 |
| 申请时段 | 订单提交时用户选择的时段，未保证名额 |
| 确认时段 | 人工确认正数收款或人工零元结算成功后确认的时段 |
| 自动归集组 | 同一个配送时段 ID、同一个校区 ID 下的常规自动归批范围 |
| 配送批次 | 实际组织配送的订单集合，可由管理员拆分 |
| 配送执行 | 某订单本次实际分配，必须保留真实 assignment ID 和版本 |
| 封批 | 停止向该轮批次加入新订单，固定本轮名单；不代表已完成生产 |
| 最新配送安排 | 当前对客户生效的预计安排，包含来源、版本、原因和生效时间 |

本轮不新增自动支付、抢单市场、配送员自助调度、短信、Push、路线优化或自动打印。邮件属于订单服务通知，不加入营销文案或营销订阅流程。

## 4. 时间规则：采用统一截单线

### 4.1 配置与边界

新建配送时段必须填写：名称、配送日期、预计配送开始/结束时间、开放下单完整日期时间、截单完整日期时间、预约容量、是否启用。按当前校区模型明确适用范围；若保留全校区通用时段，不强制新造校区配置系统。

本轮**不增加独立收款宽限期**。统一规则：

`开放下单时间 < 截单时间 < 预计配送开始时间 < 预计配送结束时间`

- 所有比较使用服务端时间；接单区间为 `[开放时间, 截单时间)`，等于截单时间即关闭。
- 开放/截单必须支持跨日，例如前一天开放、配送当天截单；不得只保存 HH:mm。
- 服务端使用带时区 UTC 时间戳，用户和员工按 Asia/Shanghai 展示与录入，转换仅一次。
- 截单与配送之间必须有正的准备间隔；不写死未经配置的 30/60 分钟业务值。可给出帮助说明，不把示例当生产默认值。
- 配送日期/时间变化必须重新验证相对时间关系，不能留下截单晚于配送开始的配置。
- `enabled` 仅表示人工开关；当前是否可申请必须由时间窗、容量、归档、营业暂停和封批等共同决定。

### 4.2 可申请判定

用户申请时段必须同时满足：已配置、已启用、未归档、当前在接单时间窗内、有剩余容量、服务允许新单、该时段未被提前结束接单。若时段按校区适用，还必须匹配用户所选校区。

公开可申请列表和提交订单接口必须复用同一套判定语义。前端隐藏不代替后端校验；直调 API、过期页面、恢复草稿、修改待确认订单和多标签提交也必须受限。

申请不占容量仍然保留；多个未结算申请并不保证全部能结算。满量时停止提供新的申请选项，最后名额在结算事务内竞争。

### 4.3 到点与提前封批

截单时：停止新申请，停止本轮自动入批，所有相关批次进入名单冻结阶段。到点立即生效，不能依赖定时任务及时运行。

- 可用定时任务持久化封批事实，但每个相关读写入口都必须按服务端时间执行相同限制。
- 定时任务延迟、服务重启、worker 停止，均不能让截止后的订单入批。
- 本轮第一版的“提前结束接单并封批”作用于整个配送时段，预览该时段所有校区的影响；不要隐式只关闭一个校区而让全局接单状态含糊。
- 提前封批为管理员显式动作，必填原因、版本校验和影响预览；封批后本轮不提供重新开放入口。需要新一轮接单时创建新的时段。
- 配送员不能自行提前封批。配送员在未封批时看到明确阻断与联系管理员的提示。
- 封批后只要发布、付款、生产、装袋、地址等守卫通过，可以早于预计配送开始时间出发；实际出发早于预计窗口不自动改写客户预计窗口。
- 已有订单时，不允许用普通编辑延后截单来绕过封批；只可通过上述显式动作提前结束。

## 5. 确认收款、容量与自动建批

### 5.1 唯一触发点

只有现有人工正数结算成功或人工 `ZERO_PAYABLE` 结算成功才触发。客户声称已付款、上传付款凭证、管理员打开订单、单独登记待核对实收、客户接受时段建议，都不算结算成功。

一笔结算成功必须在同一业务事务里完成：

1. 校验订单、报价、内容版本、付款金额和有效状态。
2. 校验当前时段可接受结算、未截单、未提前封批、有容量。
3. 确认时段、占用一次容量、记录结算与账目。
4. 以确认时段 ID 和真实校区 ID 查找或创建自动归集组及其常规批次。
5. 新批次为规划中、未指派配送员；名称依据真实日期、时段和校区生成，不采用 demo 数据。
6. 为订单建立一次有效配送执行，关联批次；订单按现有规则进入生产，不能因有 assignment 就变成待配送或配送中。
7. 追加必要审计与可靠通知意图，提交后前端才能显示成功。

如果自动建批/分配出现内部异常，不能留下“结算成功但漏归批”的半完成状态。若实际线下款已收，需要保留的待核对实收按现有 R06 路径单独明确处理；不得把程序异常伪装成收款成功或吞掉实收。

### 5.2 后续自动加入与权限

- 同时段、同校区、接单阶段的后续结算订单自动加入该常规批次，不要求管理员逐单选择。
- 不同校区必须分批；以订单位置关联的真实 campus ID 为准，不能按楼栋名称猜测。
- 时段容量沿用现有全时段总容量。按校区分批、拆批均不复制容量，也不再次占容量。
- 常规自动批次接单阶段只做规划与指派，封批后才发布；发布代表可以组织执行，不再接新单。
- 配送员只查看分配给自己的批次。未指派批次由有 `delivery.manage` 权限的管理员处理，不暴露成全员可抢任务。
- 自动建批不自动指派、不自动发布、不自动开始、不跳过打印/装订/装袋。

### 5.3 并发与幂等硬约束

不能只写“先查再创建”。必须使用 PostgreSQL 行锁、关系约束及现有幂等机制共同保证：

- 每个 `(slot_id, campus_id)` 只有一个常规自动归集组/归集入口；允许其下存在显式拆分的多个执行批次。
- 每个订单最多一个有效配送执行，复用现有唯一约束，不能用 batch ID 代替 assignment ID。
- 同一结算请求重放，不重复确认收款、占容量、生成批次、assignment、工资或邮件意图。
- 两个管理员同时结算同一单，只成功一次；不同订单并发首次结算，只生成一个归集入口和一个常规批次。
- 同一时段最后一个容量并发竞争，只允许一个成功；失败路径真实保留应核对的已收款。
- 封批和结算竞争必须有确定先后，检查截止时间须发生在取得相关串行化锁之后；等待锁跨过截止时间的请求不得继续按旧时间入批。
- 成功结算与封批应形成可串行化的结果，不允许封批提交后再追加订单。
- 唯一冲突须正确重读/恢复，不泄漏未处理 IntegrityError，不无边界重试。

建议用一个很小的自动归集组表保存唯一键、常规批次引用和封批事实；如采用不同方案，必须证明等价约束。不要对所有批次直接施加 `(slot_id,campus_id)` 唯一，导致合法拆批无法存在。

## 6. 截单后未结算与迟到账

截单前已申请但未成功确认收款的订单，不属于本批次。截单后，即使客户确实转过款，普通确认收款接口也不能绕过截止继续归入原批次。

- 对真实已收到的正数款项，沿用待核对实收记录，返回可处理的业务冲突并显示款项已登记；重复请求不能重复记款。
- 未实际收款或零元结算受拒时，不伪造实收流水。
- 允许在原订单上提出其他有效时段建议，客户确认后、目标时段仍可结算时，使用原待核对实收完成一次结算，不能要求再次付款。
- 接受时段建议不直接占容量；结算仍需重新校验，目标变满需重新协调。
- 不静默移到下一时段，不自动取消实收，不自动退款，不复活已关闭订单。
- 原有未结算超时关闭规则保留。已关闭订单收到的款项按现有线下退款/重新下单路径处理。
- 用户下单页和待确认订单页说明：申请不保证名额，以截单前管理员确认收款结果为准；展示具体截止日期时间，不能只写“尽快付款”。

## 7. 名单与批次状态：保留现有主状态机

封批状态与现有批次状态正交。优先增加 `sealedAt/sealedBy/sealReason` 等明确事实，别为方便重写所有订单状态。

| 情况 | 可做的事 | 禁止行为 |
|---|---|---|
| 规划中、未封批 | 自动入批、管理员指派与查看准备进度 | 发布后继续接单、配送员直接出发 |
| 已封批、规划中 | 检查准备、管理员明确拆分/改派/改期、发布 | 普通自动入批 |
| 已发布 | 当前配送员/有权管理员按现有守卫开始 | 自动追加订单 |
| 配送中 | 逐单交付、异常记录、未送达订单延误更新 | 加单、改写已送达事实、整批倒退到规划中 |
| 已完成/取消 | 查询历史、按现有规则售后 | 自动复活、重新吸纳普通订单 |

全部生产、装订、人工装袋、地址复核、退款锁、阻断异常、有效配送员和有效执行版本检查继续有效。

如果部分订单未就绪，整批开始仍按现有 Q17 守卫阻断。管理员可明确选择订单拆分，保留未就绪订单去向、原因和客户通知；不能静默漏送或悄悄只发已就绪部分。

拆分后的子批次继承时段/校区/封批信息，不能重新开放自动入单。封批后人工移单属于显式调度，必须预览来源、目标、客户影响、生产和容量守卫；已出发目标一律拒绝。

取消订单、退款、修改楼栋跨校区、售后重做和恢复垃圾桶都必须维护有效分配不变量。接单期间常规批次暂时变空时，保留归集入口，后续订单复用；封批后变空不重开。退款释放容量不重新开放已封批时段。批次删除不能使仍需配送的已付款订单孤立。

免费重做/补送沿用既有售后及工资规则，由管理员显式安排，不能套入普通确认收款事件来重复收款或重复自动计件。

## 8. 改期：原承诺与当前安排都保留

### 8.1 单一权威读取

保留原申请、结算确认时段和其完整快照。新增/完善订单“当前生效配送安排”视图，由后端集中计算，至少返回：当前预计窗口、安排状态、当前批次引用、安排版本、公开原因、更新时刻和是否有待确认的新时段建议。

- 客户订单页、列表摘要、管理员详情、配送端和邮件读取同一有效安排；不得各自从原 slot、batch JSON 或本地列表拼接出不同答案。
- 尚未指派配送员或尚未发布时，明确显示“预计时段已确认，待安排配送员”等真实状态，不把内部规划写成已出发。
- 没有有效执行时，根据确认时段/申请时段显示对应语义，不依赖公开可申请列表才能显示历史。
- 历史确认快照不随当前时段编辑变化。旧版快照不完整时使用有来源标识的安全回退，不凭空补造原承诺。

### 8.2 两种时间变化必须区分

**A. 当前执行预计时间更新/延误事实**：运营方更新预计送达窗口，必须填写公开原因、记录前后时间、更新未送达订单并通知。原确认时段保持历史记录，不伪造客户同意。

**B. 改订到另一个预约时段或另一天**：走客户确认建议。客户未确认时，页面同时显示原确认记录、“原安排延误/需协调”和“建议的新时段待确认”，不能把建议时间显示成已确认。

- 同日运行中的预计延误可以直接更新并通知；跨日安排必须走 B。不得通过把跨日改订命名为“预计时间更新”绕过客户确认。
- 原安排已经无法履行时，延误事实立即通知，不能等客户同意才告知；建议新时段不代表已生效。
- 对已结算订单支持同样的确认机制，但不重新收款、不改报价、文件或原付款事实。
- 客户接受已结算订单改订时，原/目标容量和有效执行迁移必须原子完成，目标仍须有名额、未封批、未出发且允许接收；目标失效则明确冲突，保留待协调状态。
- 同一时段内只拆分执行批次或更新 ETA，不重复增减时段容量。
- 客户拒绝或未回应时，保留待协调和管理员处理入口，不自动同意；不能将明显不可履约的旧安排展示成正常待配送。
- 管理员改派/跨校区地址复核不得悄悄改变已确认时段。封批后跨校区无法合法迁移时，进入异常协调，不自动另建可接单批次。

### 8.3 统一变更入口

- 无任何订单引用的时段可直接修改时间，但仍做版本和合法性校验。
- 有订单引用后，时段页普通编辑不能覆盖原预约时间；“调整配送安排”进入影响预览，区分待结算申请、已确认未送达、已送达和多个校区批次。
- 批次编辑、批量 RESCHEDULE、时段级改期、转移/合并造成 ETA 改变等入口必须使用同一变更服务，不能只修一个按钮。
- 待结算申请受影响时写入公开变更提示和通知；修改其申请目标仍走建议确认，不静默改写选择。
- 预览列明影响订单、状态、前后时间、容量、确认要求、通知对象和阻断原因。预览不产生实际修改或邮件。
- 提交时重新校验 plan、资源版本、权限和当前事实；过期计划/预览后新增订单导致影响集合变化时拒绝旧提交并要求重新预览。
- 内部草稿不对外生效、不发客户通知；正式提交才同时改变有效安排和记录通知意图。再次发布不重复发送同一个改期事件。
- 仅改名称、内部备注、无实际变化的时间不触发客户改期邮件。
- 对配送中的批次，仅更新仍未送达订单的 ETA/异常安排，保留已送达记录；不得用旧 RESCHEDULE 把整批改成 POSTPONED 并破坏执行。

## 9. 邮件：复用现有设计与可靠队列

优先扩展已有 `DELIVERY_UPDATED`，不复制第二套模板系统。需要不同“建议/已生效/延期待安排”内容时使用明确变更类型与真实状态；是否新增模板 key 由契约可维护性决定，但共用现有 shell、模板编辑、预览、测试和默认恢复机制。

邮件至少表达：品牌、订单提取码/可公开订单号、变更类型、原配送完整日期时间、新配送完整日期时间或“待重新安排”、客户可见原因、是否需要确认、订单查看按钮、备用链接与现有页脚。

- 客户邮件不展示同批其他客户、内部批次名单、电话、私有文件或内部备注。
- 复用现有暖色、品牌、字体、留白、卡片和按钮；同时更新后端默认 HTML、纯文本、前端预览/导出来源，核查 `scripts/export-mail-templates.py` 的同步方式，不能两套样式漂移。
- 为已经结算的通知移除“请先完成付款”；待结算、零元、已生效改期和待确认建议各用准确文案。
- 使用数据库持久化变更事件/通知意图，与业务变更同事务提交；worker 通过现有 EMAIL/outbox 机制处理，SMTP 故障不能回滚已生效安排。
- 现有 `_queue` 失败可能静默返回 None。不得让通知意图静默丢失；即使模板损坏或 SMTP 未配置，也要能从持久化事件恢复、看到失败原因和安全补发。
- 以“变更事件 ID＋订单 ID＋通知类型＋接收方”作为稳定去重依据，不以任意 order.version 变化无限触发重发。
- 单次业务提交/重放不重复建任务；SMTP 不可能保证端到端 exactly-once，受理后断连按未知结果处理，不宣称绝无重复投递。
- 明确区分待发送、SMTP 已受理、失败、结果未知、无可用邮箱。除非有真实回执，不能显示“客户已收到”。
- 有有效已验证订单账号邮箱才发送；游客/无邮箱/账号失效的订单显示未发送原因，订单内留提示并给有权管理员人工联系入口，不新增游客邮箱收集。
- 现有模板启用开关/业务通知配置必须有明确语义并显示。重要变更即使因关闭配置未投递，也保留可见事件与“未发送”原因，不能声称全员已通知。
- 通知当前受影响的配送员；改派时原配送员应看到任务失效，新配送员看到新安排，不继续保留原执行权限。
- 邮件正文不得包含一点击即生效的同意操作。确认链接进入有权订单页，经过认证/授权后由显式写请求完成，GET 预取不消费确认。
- 后台已有自定义模板不静默覆盖；采用向后兼容变量升级及可见升级提示，验证旧模板和恢复默认行为。
- 连续两次真实改期保留两条历史；发送任务携带事件时间和版本，页面始终指向最新安排。不得以发旧任务为由覆盖最新安排。

## 15. 事务、锁与安全

本轮会把结算、slot、group、batch、order、assignment 连在一起，现有调用可能采用不同锁顺序。**必须画出并统一这些入口的锁顺序，覆盖正常路径和异常/退款路径，避免新死锁。** 不可只在结算函数末尾增加一个 batch 锁就认为完成。

- 覆盖结算、封批、开始配送、退款取消、拆合移单、客户接受改期、地址复核、归档和垃圾桶恢复。
- 当前端或客户接受方案传入多个 ID 时，按稳定顺序锁定；锁等待后的版本、时间、权限与目标状态重新检查。
- 未经提交的查找结果不能作为最新容量/开放/assignment 依据；后台预览也不是提交凭证。
- 使用现有 request session 事务、DomainError、审计、CSRF、Origin、幂等键和统一错误信封，不再造第二套提交框架。
- 纯 `payment.manage` 账号确认收款可以由服务执行必要自动归批，不要求同时持有 delivery.manage；但不能读写任意调度数据。
- 客户只能读取/确认自己或有效单订单授权允许的方案；配送员只能当前分配；邮件管理员不因此取得订单调度权限。
- 公共 API 不返回订单名单、客户资料、内部原因、审计、邮件地址或私有文件。
- 改期不改金额、报价、优惠、文件确认、打印事实或已送达工资；需退款/重做走现有售后路径。

优先扩展现有端点和 DTO，维护现有路由。新增封批、ETA 变更、已付款时段建议/确认所需端点必须有明确 DTO、权限、版本和错误契约，不使用任意 payload/status 覆盖。

至少提供：

- 时段开放/截单时间、接单状态、可申请布尔值、阻断原因、容量与版本。
- 批次来源（自动/人工拆分/售后）、slot/campus/group 标识、封批事实、准备统计和允许操作。
- 订单原申请、确认快照、当前有效安排、待确认建议和最近公开变更。

错误码需区分未开放、截单、提前封批、满额、目标已出发、配置缺失、版本冲突、预览过期、等待客户确认、无权限以及已登记待核对实收；命名可复用已有代码但语义必须可测、中文文案可操作。

由真实 FastAPI OpenAPI 运行 `npm run contract:generate` 更新 `docs/openapi.yaml` 与 `src/lib/api-schema.d.ts`，检查生成脚本，不手改生成物，不在脚本虚构服务端路由。同步所有受影响前端类型、store 适配和 demo 夹具，真实模式没有 demo 成功回退。

## 18. 实施顺序与阶段交付

每阶段先写能揭露真实风险的失败测试，观察失败，再实现并验证。并发和事务测试必须使用 PostgreSQL，SQLite 不能代替。

- [ ] A. 盘点与契约：列出现有入口、锁顺序、状态与数据来源，确定 DTO 和迁移，保护工作区。
- [ ] B. 时间窗：实现统一资格判定、边界、封批与旧数据兼容；完成前后端目录分离。
- [ ] C. 自动归批：结算事务接入 group/batch/assignment，完成容量、幂等、并发和退款取消联动。
- [ ] D. 安排与通知：统一有效安排、变更预览/提交、客户建议确认、持久化事件与邮件恢复。
- [ ] E. 三端交互：按本文落实时段、调度、收款、用户订单和配送端所有状态与权限。
- [ ] F. 完整联调：迁移、生成契约、测试、构建、真实隔离环境浏览器验证、报告。

如果环境不足，完成可做部分并准确报告阻塞，不把 mock 或纯文档当全链路完成。不要因一项外部 SMTP 条件不足而跳过本地代码、失败恢复和模板验证。

## 19. 必须覆盖的后端验收矩阵

以下均需有可复现断言，不是只写手工“看起来正常”：

1. 开放前不可申请、开放时可申请、截单前可申请、等于/晚于截单拒绝；跨日和上海/UTC 边界正确。
2. 公开列表隐藏不可选，直调 API、旧页面、编辑待确认订单均不能绕过。
3. 有申请未付款不建批、不占容量；单独实收登记不建批；确认正数收款和人工零元结算各能建批。
4. 同时段同校区后续结算自动入同一常规批次；不同校区各建批，共享时段总容量。
5. 两笔首次结算真实并发，只建一个 group/常规 batch，两个正确 assignment；同单并发只结算一次。
6. 相同幂等键重放、不同键重复结算、最后容量并发竞争无重复/超售。
7. 等锁跨过截止时间拒绝；结算与封批并发结果可串行化；定时任务未运行也不能越过截止入批。
8. 截单后待确认/迟到账款正确登记、可用原实收协调新时段、不重复收费；已关闭订单不复活。
9. 未封批不能发布/开始；封批后可早于预计开始时间出发，且所有现有生产守卫仍然有效。
10. 已封批/发布/配送中/完成批次不能普通自动加单；手工接口也不能绕过。
11. 空批次复用、封批后退款释放名额不重开；取消/退款不留下有效孤立 assignment 或孤立已付订单。
12. 拆批继承封批和归集身份，容量不变；合法拆批不被错误唯一约束阻断。
13. 多入口 ETA 变更统一有效安排；原确认快照不变；跨日改订不得绕过客户确认。
14. 待付款与已付款建议各自确认正确；确认目标变满/截单/出发时冲突；已付款迁移容量原子且不重复收款。
15. 预览不发邮件、不修改业务；预览后订单集合/版本变化拒绝旧计划；同计划重复提交安全。
16. 已出发部分送达后更新 ETA，只影响未送达；历史交付、工资、照片授权不变。
17. 正式改期记录准确旧/新时间与公开原因；无变化、内部改名、重新发布不重复通知。
18. 业务回滚不遗留邮件意图；业务成功后 SMTP 不可用意图仍可恢复；SMTP 接受/失败/未知状态真实。
19. 模板自定义、缺变量、恢复默认、HTML/纯文本/前端预览升级正确；无邮箱可观察、可人工跟进。
20. 双次连续改期、worker 延迟/重试/重启不覆盖最新安排、不重复生成同事件任务。
21. 客户、游客单授权、payment-only 管理员、delivery-only 管理员、mail-only 管理员与配送员的允许/拒绝路径完整。
22. 改派、跨校区地址、旧 assignment 提交、批次恢复和售后补送不破坏唯一执行或工资规则。
23. 真实并发覆盖退款/结算/封批/开始等锁链，测试有超时边界，不将挂死当通过。
24. 旧时段无接单配置、旧多个批次、脱关联、已送达/退款/垃圾桶迁移可查询且不静默重排。

## 20. 必须完成的浏览器与 UI 验收

至少完成并记录以下场景，桌面与 390px 移动视口都检查主要页面：

- 新建跨日接单时间窗，验证字段错序、缺值、容量错误、首个错误聚焦和保存反馈。
- 用户选时段 → 提交 → 管理员确认收款 → 自动出现批次 → 再确认一单自动加入；未付款单不混入配送清单。
- 指派 → 接单期间不可出发 → 提前封批/自然截单 → 准备检查 → 发布 → 预计时间前出发 → 单单和批量交付。
- 等待页面跨过截单点、休眠恢复、两标签、弱网和失败重试；失效选择有解释，其他输入保留。
- 截单后确认款项 → 待核对实收 → 新时段建议 → 客户确认 → 使用原实收完成结算。
- 同日 ETA 延误、跨日建议待确认、客户拒绝、目标满额、已送达部分不受影响。
- 管理时段关闭后历史订单/批次仍可读；用户列表不再出现不可选项。
- 邮件模板预览实际前后时间、原因、长文本和移动宽度；SMTP 失败/无邮箱状态可见，补发有防重。
- 后台静默刷新不白屏、不打断编辑；仅有收款权限账号不能通过成功链接进入调度；旧配送员改派后无法提交。
- 长名称、长原因、320/375px 窄屏抽查、大字体、键盘焦点、Esc、减少动画、弹窗快速开关和移动软键盘不破坏布局。

Playwright 拦截接口只证明 UI 行为，不能替代数据库/事务/真实后端联调。至少一条“下单—收款—自动归批—封批—出发—交付—改期通知记录”相关链路需使用隔离真实后端与测试数据；已交付订单不再改期，改期分支使用尚未交付的另一笔订单。
